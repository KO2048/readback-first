# 正式对话优先：修复与证据边界

Plan Version: plan-v11. Issue #27. Baseline v0.8.3; candidate v0.9.0.

## 历史要求提取缺口

用户早已要求“正式答复正文、无需展开thinking/工具/折叠状态”。旧版Reader-facing
段落保留了最终正文要求，却使用“a short progress receipt may precede tools”。
旧fixtures还由readback_shown等布尔量表示完成，未检查消息顺序和显示位置。

此前27份样本的首轮含“先给理解/先回讲”提示，不能代替自动默认入口验证。
本次将历史要求落成入口优先规则、协议§0、宿主映射与事件顺序检查，而不只增加
重复的原则段落。[要求追踪](requirements.md)。

## 失败模式与确定性测试

用户提供的WorkBuddy截图中，正文以行动通知开头并先执行核查；思考区的意图
分析不能替代正式回讲。截图不是v0.8.3实测，不能把它写成最新版已复现。

13项编写的消息事件测试覆盖：思考区、折叠状态、进度区、仅行动通知、任务工具
抢先、结尾才回讲、最终正文漏回讲、回答先于回讲、伪装引导加载、显示位置未知、
空回讲，以及正常顺序和显式直答例外。空实现先失败10项，实现后13项通过。

`delivery_trace.py`检查事件的顺序与位置，不自动识别语义。消息位置与折叠状态
必须来自真实宿主/界面观测，语义片段角色由审阅者标注；不能把模型自报作为输入
证据。未知位置只能未验证。原39项fixtures保留，不能把13项新工具测试计作模型
13次成功。

## 不带回讲提示的实际任务

任务仅要求比较tests/delivery/materials的两份材料、判断是否有助理解及汇总调整；
没有提示“先回讲”。测试包装仍明确加载Skill，不代表自动发现或每轮激活验证。
两个参与者复用旧上下文，同宿主，不能独立归因。

- [旧版事件](baseline.json)：先在commentary回讲，读取契约与材料，再在最终正文
  回讲并回答。通道顺序可核对，但commentary是否持续显示在正式正文未知，不计通过。
- [候选事件](candidate.json)：读取契约后在最终正文回讲请求与未知，说明无法确认
  正式前置显示，因此未读取任务材料。它没有要求重新确认。这验证了限制出口，
  不是正常执行路径或所有宿主显示验收通过。

本记录只保留消息和工具事件，不公开思考内容。本机路径替换为占位符；hashes.json
校验的是脱敏后的记录。没有把缺失UI字段补成“正式正文已显示”。
